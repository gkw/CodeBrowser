## Model record

### `gpt-oss:120b-cloud`

Status: completed  
Review scope: architecture feasibility, streaming metering, idempotency, usage ledger, price versions, auth, replay and sharing, SSRF/request smuggling, quotas, privacy, reconciliation, and staged MVP.

Response summary:

- Judged the middleware approach feasible and agreed that only the middleware should hold the Ollama key.
- Identified final-frame token accounting, idempotency, concurrent spend, source-code leakage, client distrust, fixed upstream routing, payload limits, price versioning, and reconciliation as major concerns.
- Proposed an append-only usage ledger, per-user concurrency limits, short-lived authentication, Stripe idempotency, and a staged implementation.

Accepted recommendations:

- Use Ollama's upstream `prompt_eval_count` and `eval_count`, never client-provided counts.
- Keep the Ollama key exclusively in middleware and hard-code/allowlist upstream destinations.
- Enforce payload, operation, model, concurrency, quota, and global spend limits before contacting Ollama.
- Use database uniqueness for idempotency and immutable price versions.
- Avoid logging or retaining source-code prompts and responses.
- Reconcile product usage, billing delivery, and provider-level usage where available.

Modified recommendations:

- **Entire-response buffering:** rejected as unnecessary and memory-intensive. Stream safe chunks while parsing NDJSON; retain only bounded operational state. The final usage frame is the commit point.
- **Discard usage after client disconnect:** rejected. The vendor may still incur upstream cost. The MVP should drain the bounded upstream stream to obtain final counts, or record `metering_unknown` if authoritative counts cannot be obtained.
- **Prompt-hash idempotency:** rejected as the primary key because users may legitimately run the same prompt twice. Use a random logical-operation key scoped to the actor and a server request ID; store a prompt digest only for privacy-preserving correlation.
- **Client HMAC signing:** rejected because a distributed client cannot safely hold a shared signing secret. Use TLS, authenticated sessions, short expiry, server-side authorization, and replay-safe idempotency.
- **Device fingerprint binding:** downgraded to an abuse signal, not authentication; fingerprints are unstable, spoofable, and privacy-sensitive.
- **Per-request Stripe charges:** rejected. Use an internal ledger plus transactional outbox and Stripe meter events with stable identifiers. Billing delivery is asynchronous and must not decide an already-streaming response.
- **In-memory active stream count:** insufficient for multiple wrapper instances. Use a shared lease/counter or database-backed reservation with expiry.
- **Provider reconciliation API:** treated as unverified. No claim is made that Ollama currently provides a suitable account-level token export.

Resulting implementation changes:

- Added `docs/metered-ollama-wrapper.md` with the corrected architecture, freemium policy, request lifecycle, ledger, security controls, billing flow, Go/No-Go gates, and staged rollout.
- Added this project-local review register and record.
- No runtime code, production billing, or customer authentication was implemented in this review.
